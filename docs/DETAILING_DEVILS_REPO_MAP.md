# Detailing Devils — current source repository map

This map describes the current Laravel checkout. The original `devils-new-web.zip` is a historical baseline; inspect the checked-out source whenever a detail here may have changed.

## Project at a glance

- Laravel 13 / PHP 8.3+, Blade, plain CSS and browser JavaScript.
- The homepage uses a shared website layout, shared Blade components, a homepage view, and CSS/JS files served from `public/assets/`.
- GSAP 3.12.5, ScrollTrigger and Lenis 1.1.13 load from CDNs on the homepage. The scroll-driven canvas uses the owner-supplied 121 JPEGs in `public/frames/`.
- Vite/Tailwind are configured in `package.json`, `vite.config.js`, `resources/css/app.css` and `resources/js/app.js`; the current homepage does not load those Vite entrypoints.
- The backend provides disabled-by-default CRM enquiry submission, optional email notification, and a token-protected deployment route.

## Directory and file ownership

Laravel HTML error views live in `resources/views/errors/`: explicit 403/404/419/429/500/503 pages and generic 4xx/5xx fallbacks share noindex `layout.blade.php` and `content.blade.php`. The slim shell reuses the actual `header`, `navbar` and `footer` components, existing `style.css`, fonts and `navigation.js`; those presentational components use only configuration and route/asset helpers. Even 5xx views omit the full app layout's session notifications, CSRF meta and form/vendor helpers, requiring no database/session/authentication service. Home/footer links and a noscript navigation remain usable without JavaScript. Status/header handling, API/AJAX JSON and validation behavior remain Laravel's defaults; production debug must stay disabled. Apache/edge-generated errors bypassing Laravel are outside these views. `tests/Feature/ErrorPagesTest.php` covers rendering, fallbacks, safe disclosure, shared components and preserved JSON/validation behavior.

`errors/illustration.blade.php` supplies eight predefined, validated inline SVG variants on a shared automotive-studio drawing. `content.blade.php` maps status codes to these variants; unknown variant inputs use the safe system illustration. Artwork has its own accessible title/description and needs no external image, font or JavaScript. Common composition and scoped styles remain in the shared content/layout, so visual changes propagate to every error view.

503 is the exception to the site shell: `errors/503.blade.php` is a standalone maintenance document with inline CSS, the existing maintenance SVG include and an embedded official logo. It resolves `site.brand`, `site.phone`, `site.phone_link` and `site.support_email` at render time, with no new contact keys or external assets/scripts. Normal 503 handling uses it automatically; Laravel 13 also supports `down --render=errors::503 --retry=120` for pre-bootstrap delivery. Pre-render again after config/contact updates; omit `--refresh` to avoid automatic reloads. `tests/Feature/MaintenancePageTest.php` tests the actual down/up flow only in temporary isolated storage. No default-project or live maintenance state is changed by QA.

## Rendering and asset order

`GET /` → `HomeController::__invoke` → `home.blade.php` → `layouts.app`. The layout emits one HTML document, `<x-header>`, `<x-navbar>`, one `<main id="top">` containing `@yield('content')`, and `<x-footer>`.

The layout loads fonts, optional non-homepage Bootstrap/Bootstrap Icons/Tom Select CSS, SweetAlert2 CSS, `style.css`, then page CSS from `@stack('css')`. At the end of the body it loads local Axios and SweetAlert2, optional non-homepage Bootstrap JS, common utilities (including `location.js` after shared Axios), `<x-notification>`, `navigation.js`, then `@stack('js')`. The homepage stack adds CDN GSAP/ScrollTrigger/Lenis, `window.DD_SERVICES` and `window.DD_FRAMES`, then `home.js`. The homepage adds `home.css` through the CSS stack. Bootstrap and Tom Select are deliberately excluded from `/` by the layout's `request()->is('/')` condition.

`home.js` uses the hero frame URLs generated from `config/site.php` and `public/frames/`; it draws into `#cv` as scrolling advances. It creates six service buttons and images from `DD_SERVICES`, coordinates with the shared menu through `dd:menu-toggle`, and sets up Lenis/ScrollTrigger when motion is enabled. Keep the asset order and element IDs in mind when changing the layout or homepage.

The adaptive loader replaces the two eager sequence loaders while retaining their canvas renderers, scroll interpolation and effects. Its existing loading strip reports readiness of the initial working buffer, rather than downloading the complete sequence first. `tests/js/frame-loader.test.js` covers prioritization, bounded resource retention, reverse/replay access, cancellation, lifecycle restoration and image fallback. The Phase 2 refinement avoids sorting/scanning exact cache hits, evicts obsolete frames first and uses native JPEG rendering plus scale-dependent native/bitmap AVIF rendering to preserve canvas filtering. Normal download limits adapt to the cache/codec: Home uses four on desktop/two on compact screens, Tour uses two on desktop/four on compact screens; slow connections cap both at two. Resource versions invalidate resized/replaced images; decoded resource budgets remain 96/160 MiB, with a 40 MiB compressed cache. See `docs/ANIMATION_PROTOTYPE_PHASE_2.md` for historical measurements and `docs/ANIMATION_PROTOTYPE_V2_1.md` for the approved refinement, remaining limitations and rollback baseline. The supplied Chrome audit artifacts under `docs/dd-animation-audit-*/` remain local reference material.

V2.1 adds one planned nearest-available fallback from already downloaded data when the directional decode window cannot satisfy the target. Exact work retains priority and reserved capacity within the same cache/decode budgets; useful late completions can be reused. Bitmap disposal remains immediate. Frozen V2 sources are in `docs/animation-benchmarks/*-v2.js.txt`; repeated V2/V2.1 measurements and limitations are in `docs/ANIMATION_PROTOTYPE_V2_1.md`.

## Homepage content and data

The homepage view owns the hero, introduction, approach, statement, statistics, services, work animation, studio cards, five-car lineup, franchise section and enquiry section. Shared header, menu and footer markup live in their components. Shared style rules live in `style.css`; section rules live in `home.css`.

`config/site.php` supplies the hero text/frame pattern, statistics, services, brand/contact details, social destinations and franchise steps. The franchise CTAs and other section copy are in `home.blade.php`. Images are under `public/img/`; frame files follow `ezgif-frame-001.jpg` through `ezgif-frame-121.jpg`; no second root JPEG sequence is retained.

The Prime button uses the named `prime.show` route, which renders the migrated five-step frontend at `/detailing-devils-prime-form`. The homepage FOFO button uses the named `fofo.show` route; the FOFO form is available directly at `/franchise-owned-franchise-operated-model`, but its submit button and POST handler remain disabled until `FOFO_SUBMISSION_ENABLED=true` is explicitly configured. Shared read-only location GET endpoints use `tbl_country_phone.id` → `tbl_states.country_id` → `tbl_cities.state_id`; tests use isolated SQLite fixtures. Prime submission is disabled by default through PRIME_SUBMISSION_ENABLED. When enabled, it validates the form, consumes a purpose/mobile/session-bound OTP proof, and saves a new legacy CRM lead or returns an existing-lead result. OTP endpoints require SMS Alert credentials and both readiness flags; Prime-purpose OTP sends also return HTTP 503 while Prime submission is disabled. Only newly created Prime leads schedule two independent, best-effort emails through Laravel termination callbacks after the save commits; no queue or durable retry is used. The team recipient comes from `PRIME_FRANCHISE_TEAM_EMAIL`, and the sender uses Laravel's `MAIL_FROM_*` settings. The `log` mailer skips Prime emails so applicant details are not written to application logs.

`PrimeController::create` passes `config/form_options.php` choices to the Prime view; `StorePrimeRequest` reads the same allowed values and uses `PhoneNumberNormalizer` to verify mobile and WhatsApp inputs. Validated requests expose canonical E.164 values through `normalizedPhoneNumbers()`. `PrimeController::store` passes those values to `SaveFranchiseLeadAction`. Prime selects its record type and mandatory mobile OTP verification in backend code; its field mapping stays separate from the shared duplicate check and insert. The shared path invokes the form-defined verification callback inside the locked transaction, including for duplicate leads. The action locks by `(record_type, phone)`, but the legacy CRM has no unique constraint on that pair, so other writers that do not use the lock can still create duplicates. The current database queue uses the default database unless separately configured; do not dispatch email jobs to the CRM connection.

Public FOFO submission remains disabled by default.

## Franchise form ownership

FOFO and X-Clusive own separate Blade questionnaires, JavaScript entry policies, request rules/messages, option lists and CRM questionnaire mappings. The approved fields and row output remain identical. Only contact/location Blade sections, full-name/phone normalization and low-level frontend/persistence mechanisms are deliberately shared. Do not make one request inherit the other or route X-Clusive back through the FOFO questionnaire mapper.

Both views retain the legacy CSS classes and control IDs to preserve appearance. The form carries `data-franchise-model`; each entry checks it before initializing, and the shared engine prevents duplicate initialization. Scope future model-only styling using that marker (or a body `:has()` selector) rather than changing common rules. Shared phone-country history and email-proof behavior remain unchanged. New questions still require coordinated model-specific frontend, request, mapper and email review; they do not automatically create CRM columns.

Deploy the shared JS engine, both entries, both views/partials, controllers, sibling requests/base, option configuration and save action as one coordinated release. Script URLs carry content-hash versions so new views cannot reuse a cached pre-separation entry. Old views do not load the new engine/marker, so partially replacing entry files can interrupt initialization. Make all dependencies available before exposing the new views, refresh compiled Blade/configuration and PageSpeed caches through the existing release process, and verify both models. Routes, flags, recipients, CSS, Prime and database schema require no change.

## Central SEO and simplified administration

Public metadata flows from actual routes/content providers and the authorized database publication through `SeoResolver` -> typed `SeoMetadata` -> `SeoComposer` -> the shared `<x-seo-head>` in the application and Prime layouts. `config/seo.php` contains only trusted origin, locale, global defaults, discovery exclusions and content-type templates. There is no manually maintained page registry, per-page config metadata or Blade title/description compatibility override. Published metadata remains authoritative; absent/invalid publications and storage failures use generic route-derived metadata. Future content records retain their typed source metadata and templates. The shared head performs no database queries, while errors/maintenance remain independent.

The foundation retains production canonicals, the approved Tour query policy, OG/Twitter metadata, approved image manifests, typed JSON-LD, content adapters, validated sitemap generation and diagnostics. `DatabaseMetadataRepository` reads one atomic publication snapshot per resolver/request from the unchanged default connection. Existing publication JSON and database schema are unchanged. Company/email branding remains separate from page SEO; no franchise controller, questionnaire, email template or frontend behavior changes are required. Duplicate copy produces ordinary reviewable warnings rather than a hardcoded per-page configuration exception.

`SeoRouteDiscovery` inspects actual public HTML routes; no page registration list is consulted. `Route::view` pages and actions explicitly returning the View contract, including invokable controllers, are discovered automatically, with URL-derived titles/descriptions until editorial metadata is published. Named routes provide stable IDs; unnamed pages use a deterministic URI hash, including after Laravel assigns generated route-cache names. Discovery never executes handlers or probes URLs. A Blade file without a route creates no entry. Ambiguous/untyped controller actions need one declaration on the route: `->defaults('_seo', ['public' => true])`. The same optional route metadata supports `public => false`, robots/sitemap defaults and explicit query variants; no additional page list is needed. Standard authentication/authorization, internal prefixes, API/redirect/error routes, missing views, external domains and unknown custom middleware are excluded conservatively. Noindex pages remain manageable in the authenticated dashboard but never enter the sitemap.

Parameterized routes are not expanded or guessed. Implement the existing typed `ContentMetadata` contract through `ContentMetadataProvider::pages()` and register one real source adapter in `seo.content_providers`; `DatabaseMetadataRepository` merges those live records with the published SEO snapshot. No content records are persisted into the SEO tables. Providers are empty by default: the existing locator has no detail route, so no studio detail URLs are invented. Deleted/protected routes and removed content disappear; unpublished/noindex records never enter XML. Source-required noindex cannot be relaxed by SEO overrides. An unchanged self-canonical inherits the current route/slug, so routine editorial changes do not freeze obsolete dynamic URLs; intentional aliases remain explicit and excluded from XML. Revision restoration still validates the current canonical policy.

`GET /sitemap.xml` is declared in `routes/web.php` with `withoutMiddleware('web')` and served by `SitemapController` outside the session/web middleware, using the same current route registry, content providers and valid published metadata as the public head and dashboard. It automatically reflects publication, rollback, newly discovered routes and source-record additions/removal/indexability. ETags and mandatory revalidation prevent stale generated output. Storage/provider failures return a safe retryable 503 rather than a misleading sitemap; ordinary HTML retains its established metadata fallbacks. The approved thirteen-URL baseline is retained only in `tests/Fixtures/seo/sitemap.xml` for independent regression checks; runtime code does not read an XML reference file. Sitemap output has no priority values or fabricated modification dates. URL comparisons validate unique canonical sets without treating XML entry order as significant. There is no physical `public/sitemap.xml`, scheduler or runtime sitemap-file write. Apache's existing Laravel fallback and Wasmer's front controller handle the same endpoint; Anybuild and Apache configuration are unchanged. During the controlled Apache release, back up and remove the old physical sitemap or it will mask Laravel; clear route/config/view and relevant edge/PageSpeed caches, then verify normal GET headers and XML. Wasmer's new Git artifact naturally omits the old file. Both hosts must read the intended shared publication/content state.

`seo:sitemap` validates without writing by default, with optional atomic exports only to an explicit `--output` path. It refuses exports that would recreate the masking public file. `--restore-published` is an optional historical export, integrity-checked and rejected if its URLs are obsolete; legacy priority elements are removed from the export without changing the stored snapshot. These exports do not control the public endpoint. `SitemapArtifact` requires an explicit export path; there is no separate SEO Admin configuration or default artifact path. No changes to robots.txt, canonical origin, existing titles, Google verification, franchise routes or public Blade SEO sections are required.

Studio Tour query variants are declared once in its route-level `_seo.variants` policy and used by both discovery and request resolution; explicit X-Clusive, invalid model and tracking parameters still canonicalize to the clean Tour URL. Warranty Terms is indexable and included in the sitemap by default; valid published sitemap, robots and canonical overrides remain authoritative. All thirteen identities and thirteen canonical sitemap URLs are discovered from routes. The legacy `pages` configuration and priority fields have been retired. New supported routes require no config or XML registration. Before deploying this retirement, use the existing SEO Admin draft/preview/publish workflow to preserve any approved legacy title/description not already published, reviewing Apache and Wasmer independently because their databases are separate. Preserve existing editorial overrides, images, canonical/robots/sitemap policy, drafts and revisions; do not replace the publication snapshot wholesale. Publish reviewed changes sequentially with current version checks. Missing publication data and outages deliberately use generic metadata after retirement, while sitemap storage failures retain the retryable 503 response. No production transition is performed by source deployment, a migration or a new command.

The application timezone is `Asia/Kolkata`. New application timestamps follow that timezone; this source change does not rewrite or convert existing stored values.

### Storage, authentication and media

The owner-approved default MySQL connection is unchanged. `config/auth.php`, `config/database.php` and `config/filesystems.php` retain their verified versions: no SEO connection, separate guard or identity model. Standard `App\Models\User`, `web` authentication, session configuration and Laravel CSRF middleware are reused. `users.role` is nullable and not mass assignable. Only explicit `super_admin`, `admin` and `seo_admin` roles receive routine SEO access; null/unknown roles are denied. `manage-seo` protects every editor operation, and `publish-seo-policy` permits only Super Admin to publish canonical/robots/sitemap changes. No roles package or general account-management system is introduced. The small readiness/header middleware executes before authentication can query a missing users table, hides unprovisioned access and applies private/noindex/security headers. It does not change cookie/session configuration. Production administration requires HTTPS, debug off and the canonical Apache origin; Wasmer remains a reader.

The SEO-specific tables are `seo_metadata` (one versioned metadata/media snapshot) and `seo_revisions` (immutable baseline/draft/publication/restoration/image-approval history, linked to standard users). The canonical Laravel migration supplies `users`, `password_reset_tokens` and `sessions`. No CRM, enquiry, location, cache, jobs or studio tables are created or altered by this scoped installation. The normal Laravel `migrations` ledger is also created when the scoped installation command is eventually approved and run.

The sole users creator is the original standard Laravel `database/migrations/0001_01_01_000000_create_users_table.php`. It creates `users`, `password_reset_tokens` and `sessions`, with the standard rollback. Existing deployments must have their schema and migration ledger reviewed before any approved migration run; restoring this source does not rerun an already recorded migration.

`database/migrations/2026_11_02_000000_add_role_to_users_table.php` adds only the nullable role column to the canonical users table, preserving accounts without promotion. `database/migrations/2026_11_02_000001_create_website_seo_store.php` creates only the two SEO tables, requires users/authorization first and preflights both owned names before its first CREATE. Both now live directly in Laravel's standard migration directory; their filenames and logic are unchanged. Laravel records migration basenames, so Apache's existing entries remain valid and are not rerun because of the move. These two SEO migrations refuse destructive automatic rollback. MySQL DDL is not a single reversible transaction; investigate any partial failure against a verified backup before retrying.

Normal `php artisan migrate` discovers both SEO files in timestamp order. With all existing framework migrations correctly recorded, it applies only missing SEO migrations and skips users/sessions and previously installed SEO tables. Review `migrate:status`, schema collisions and every pending migration against a verified backup before separately approving production execution: unrelated pending cache/jobs migrations would also run, and existing but unrecorded tables or a role column without its ledger entry require reconciliation first. No production migrations are authorized by this source change. Focused tests exercise normal migration and repeated no-ops only against isolated in-memory SQLite.

Then `php artisan seo:provision owner-approved-address --role=seo_admin` can provision the first account offline; select `--role=super_admin` only for the explicitly approved owner role. It initializes metadata without overwriting an existing account; access follows the assigned role. No public registration/reset or role-edit endpoint exists. These instructions are not authorization to execute against the connected remote database.

For a fresh reader-only Wasmer SEO store, do not use `seo:provision`, which also creates a user. A separately approved one-off Laravel CLI/Tinker operation can reuse `SeoPublicationCodec::encode(new SeoSnapshot)` and `SeoSitemap::xml()`/`urls()` to initialize just `seo_metadata` row 1: production origin, version 0, empty editorial overrides/images, validated current XML, SHA-256 payload/XML hashes and update time. Require both SEO tables to be empty and use a transaction with a plain insert; never overwrite an existing publication. A fresh process/resolver then reads the new row. This creates no administrator or synthetic content and needs no new public endpoint or migration runner. The focused test verifies the approved thirteen URLs and stateless HTTP 200 after this initialization; table creation alone still yields the intended sitemap 503.

Inspect hooks before release: `/deploy` calls unscoped `migrate --force`; Composer `setup` and `post-create-project-cmd` also contain broad migration commands. CI installs dependencies/runs isolated tests, not a production migration. Anybuild delegates to Laravel-provider defaults without an explicit migration override; the active hosting/provider hook must be confirmed before deployment. None of these hooks was invoked or modified by the SEO work. Do not use them for this scoped installation.

The dashboard keeps inventory/search, drafts, previews, protected publication, revision restoration and diagnostics; editor findings inspect the actual pending draft. Login is rate-limited by IP/account. Metadata fields are validated and escaped; canonical/robots/sitemap publication or restoration additionally requires the Super Admin role, explicit confirmation and a meaningful reason. Admin and SEO Admin can publish routine metadata and draft policy proposals but cannot approve sensitive policy changes. Publication serializes on the metadata row with optimistic version checks; revisions, overrides and the historical XML/hash commit in one database transaction. There is no cross-filesystem publication dependency, and a failed transaction leaves the public metadata/XML unchanged. Read-only runtime filesystems are supported. Only use approved local output paths for optional exports during QA.

Social images reuse the existing `fofo_images` disk under `uploads/images/seo/`, already Git-ignored. The dashboard has a thumbnail library and confirmed, versioned removal for unused uploads. Published/draft/historical references protect files needed for rollback. Replace an image by uploading a new immutable URL and selecting it in the editor; clear the selection to remove a page image. Database-failure compensation restores deleted unused bytes, and upload/removal failures show a safe 503 without storage details. Private previews use the authenticated media route. They are restricted JPEG/PNG inputs, bounded in size/dimensions and re-encoded to generated JPEG filenames. Approval manifests and labels live in the SEO snapshot/revision history; no image table, new disk or storage symlink is needed. Existing franchise images and upload behavior are unchanged. Published URLs use the trusted production origin, allowing Wasmer readers to use Apache-hosted approved media; verify durable files and public delivery before activation.
